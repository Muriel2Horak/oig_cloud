### PERF-NEW-R8-C — MINOR — `SCOPE-REVISION.md:368-376` R8.7 — credential store teardown adds bounded I/O on entry-removal / provider-switch

- **Cost / where:** R8.7 binds exact credential store names: `oig_cloud.ai_<entry_id>` and `oig_cloud.solar_<entry_id>`, both created with `private=True`. The clause further mandates that "clear, provider-switch, and entry removal MUST delete both stores; neither store may collide with `oig_cloud.migration_backup_<entry_id>`". On entry-removal, that is two `Store.async_load()` calls (to read the per-store data before deletion, if needed for the audit trail) + two `Store.async_remove()` calls (HA `Store.remove` is the documented teardown verb). On a slow RPi with SD card, each Store op is 10-100 ms; the four ops total 40-400 ms on a user-driven `async_remove_entry`. The teardown MUST happen on the event loop (the user just removed the integration; HA expects the entry to be gone synchronously from a UX standpoint). R6.11 mandates cache discipline and measurable test coverage for repeated loads but says nothing about removal-time I/O; R7.2 closes secret-stripping for migration writes but not removal-time writes; R8.7 closes the store-name shape but not the removal-time cost. Without a bound, a slow SD card can stall removal by up to ~400 ms; small per-event but accumulates with other teardown paths.
- **Budget:** the entry-removal teardown of the two credential stores MUST complete in ≤ 200 ms wall time on the CI runner (averaged across 5 runs); the per-store `async_remove()` MUST observe the same 100 ms ceiling as the existing `Store.async_save()` budget implicit in R6.11. If `async_remove` exceeds 200 ms in aggregate, the test MUST fail with a metric-assertion rather than timing out silently.
- **Test:** an instrumented `tests/test_entry_removal_credential_teardown.py` (mirror of the R7.2 fail-closed test) that monkeypatches the two store construction paths, seeds keys in each, calls `hass.config_entries.async_remove(entry.entry_id)`, then asserts (a) both private store files are gone from `.storage/`, (b) total teardown wall time is ≤ 200 ms (pytest `time.monotonic()` deltas around the removal), (c) no exception is raised. Pair with the R8.7 falsification ("monkeypatch store construction for both stores, seed keys in each, call clear/provider-switch/remove, then assert exact private store keys are deleted") extended with the timing assertion.

### PERF-NEW-R8-D — MINOR — `SCOPE-REVISION.md:362-366` R8.6 — deterministic clock injection must not become a runtime branch in production paths

- **Cost / where:** R8.6 binds "tests must inject clock via explicit override path (timezone-aware now provider) and assert determinism for 2026 vs 2025 snapshots". The natural implementation is a `clock` callable parameter on the stale-warning resolver (`R7.6` snapshot selection + R8.6 clock injection). If the implementer injects the clock as a module-level singleton that is also called from production runtime paths (e.g., the `/pricelists` endpoint returning `stale_warning: true/false`), then every per-request call hits an extra function-call indirection and, worse, every test path leaves a stub clock live in memory unless carefully cleaned. A naive implementation in `step-solar.ts` or the wizard shell that calls a `now()` helper that branches on a `WINDOW` test flag will either (a) cost 1-2 µs per call in production (negligible) or (b) cause a real-clock leak in test → dev → production (a debugging nightmare). R8.6 names the contract but does not name the implementation surface.
- **Budget:** the clock override path MUST be implemented as a parameter on the snapshot selection function and as a top-level export from a dedicated test-helper module (`tests/helpers/clock.py` or equivalent), NOT as a module-level global or a conditional branch in production code. A grep `grep -rn "WINDOW\|DEBUG_CLOCK\|TEST_CLOCK" custom_components/oig_cloud/` MUST return 0 hits in production code paths (`custom_components/oig_cloud/**`); the test helper module is exempt by convention. The clock-call indirection on the snapshot-selection function MUST NOT exceed 5 µs per call (micro-benchmark via `time.perf_counter()` × 10 000 calls, p99 < 5 µs).
- **Test:** an instrumented test that imports the production snapshot-selection function and asserts it does NOT import any module whose name contains `test`, `clock_inject`, or `stub_now`. A second test runs a micro-benchmark of the snapshot-selection function with a fixed clock argument and asserts p99 < 5 µs over 10 000 invocations on the CI runner. The CI smoke matrix (per PERF-NEW-R7-B) should include a `grep` step that fails the build on any `WINDOW`/`TEST_CLOCK` symbol in production code.
