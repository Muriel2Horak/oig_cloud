# F1 Plan 3.6 — onboarding wizard completion (IMPLEMENTATION PLAN, v2)

**Scope:** Implementable plan for Plan 3.6 only. No product code changes in this task; edit only this file.

**Why v2 exists:** v1 (`2026-07-22-f1-plan3.6-onboarding-wizard-completion.md`) was reviewed by two
independent models; both verdicts were **UNSOUND**. The orchestrator verified every ranked finding
against the real tree — all hold. This revision fixes every confirmed finding, binds every task to
the `IMPLEMENTATION-BRIEF-EN.md` R6–R10 contract v1 never cited, and bakes in two human decisions
(Q1 wire schema, Q2 step-2 status semantics). Keep v1 for diff; do not delete it.

**Design constraints (fixed, human-approved — do NOT re-open):**
- `OQ-A = YES` → "Finish" persists on completion even for a `grandfathered` user who never saw the banner.
- `OQ-B = NO` → Step-2 forecast failure is soft: `[Otestovat]` never blocks `wizard-next`/`wizard-skip`.
- **Q1 — `/solar_test` wire schema:** one request body, registry key names verbatim —
  `solar_forecast_string1_kwp` / `_declination` / `_azimuth`, `solar_forecast_string2_kwp` / `_declination` / `_azimuth`,
  `solar_forecast_latitude`, `solar_forecast_longitude`, plus `provider` and the provider credential
  (`solar_forecast_api_key` OR `solcast_api_key` + `solcast_site_id`). Supports 0/1/2 active strings
  (a string is "active" iff its `..._enabled` flag is true — omit its `kwp`/`declination`/`azimuth`
  keys when inactive). Provider-specific required fields are validated server-side. No wire rename —
  the body uses registry key names exactly, so the payload can be built by iterating
  `fieldsFromRegistry(reg, 'solar')` with no translation table.
- **Q2 — step-2 status on failed/absent test:** Step-2 (`solar`) is marked **`done`** only after a
  **successful** `/solar_test` response for the values currently in the form. If the user clicks
  `wizard-next` without ever getting a successful test (never tested, or last test failed/stale
  against edited values), the step's `OnboardingState` status stays **`pending`** — not `done`, not
  `skipped` — and navigation proceeds anyway (OQ-B). `Finish` persists whatever per-step status
  currently exists; a `pending` solar step stays `pending` through Finish, it is not silently
  promoted to `done`/`skipped`. Consequence: `goNext` for the `solar` step MUST NOT call
  `completeOnboardingStep` unconditionally — it must only do so when the last `/solar_test` for the
  currently-displayed values succeeded (see Task 8).
- **Carry forward:** OQ-A = YES, OQ-B = NO (as pinned above).
