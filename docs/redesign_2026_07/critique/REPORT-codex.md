RETHINK - F1 combines mandatory AI onboarding, remote GitHub-controlled tuning, config-flow surgery, and default removal into one release, so one bad dependency, provider outage, or migration miss can lock users out or make core sensors unavailable. The design does not define enough security boundaries, rollback behavior, HA/HACS compatibility, or stale-data handling to be safely implemented. Split the work and make deterministic/manual paths and signed, constrained remote data non-negotiable before shipping.

## Findings

### 1. Contradictions & gaps

- [CRITICAL] Mandatory AI gate has no safe escape hatch. Hits F1 sections 3, 5, 8; D5, D10, D11, P1, P10. Why it breaks: new premium users cannot reach the dashboard until AI verifies, but P1 also admits model/provider failures and retry queues; "key saved, unverified" still leaves the user blocked from the thing they enabled. Suggested fix: allow a deterministic/manual completion path that unlocks non-AI premium UI, and gate only AI actions until verification succeeds.

- [MAJOR] F1 claims not to change planner/boiler logic while remote_config can change behavior. Hits F1 sections 1, 4, 7; P8, P9. Why it breaks: F1 says planner/boiler logic is unchanged, but `tuning` includes battery/boiler heuristics such as holding thresholds, cooldowns, clamps, and dead-bands. That is behavioral control, not UI configuration. Suggested fix: split remote tuning into "display/default hints" for F1 and move runtime behavior tuning to a separate safety-reviewed spec with bounds and audit.

- [MAJOR] Grandfathering conflicts with "complex modules only premium wizard." Hits F1 sections 5, 8; D9, D11. Why it breaks: D9 says solar/pricing/battery/boiler config moves exclusively to the premium wizard, while D11 lets existing users keep using the dashboard without AI and F1 disables only AI functions. There is no state table for existing user, premium disabled, premium enabled but incomplete, and imported old configs. Suggested fix: define an explicit entitlement/onboarding matrix per user state and per feature before implementation.

- [MAJOR] The single registry is underspecified for real UI fields. Hits F1 section 6; P5. Why it breaks: the current frontend has conditional boiler fields, entity pickers, secret masking, scaling, reload semantics, and field mirrors in `custom_components/oig_cloud/www_v2/src/ui/features/settings/index.ts`; F1's `Field` shape cannot represent those without reintroducing FE hardcoding. Suggested fix: extend the registry contract to include secret behavior, visibility conditions, entity selectors, display transforms, reload requirements, mirrors, and migration aliases.

- [MAJOR] Onboarding completion is not versioned or reproducible. Hits F1 sections 5, 8; D10, D11. Why it breaks: `onboarding.complete=true` in storage is treated as truth, but the design does not say which design version, field set, provider test, pricing year, or solar test created it. A future registry change can leave a user "complete" with missing required values. Suggested fix: store per-step schema version, tested provider, tested timestamp, pricing year/source, and invalidation rules.

- [MINOR] The architecture tree points at the wrong frontend root. Hits F1 section 2. Why it breaks: F1 lists `www_v2/src` at repo root, but the repo uses `custom_components/oig_cloud/www_v2/src`; implementation tasks and HACS packaging checks can target the wrong path. Suggested fix: correct the path in the design and state which files must ship inside the integration directory.

### 2. Feasibility

- [CRITICAL] Runtime dependencies required by F1 are not installable as designed. Hits F1 sections 3, 4, 5, 10; P4, O3. Why it breaks: F1 requires an OpenAI-compatible client, `pdfplumber` coordinate extraction, and XLSX parsing, but `manifest.json` currently installs only `numpy` and `paho-mqtt`; HACS/HA installs integration requirements from the manifest, not from repo dev lockfiles. Suggested fix: either implement with already-available stdlib/aiohttp only, or add pinned runtime requirements for every parser/client and validate them with a clean HA custom-component install.

- [MAJOR] HA minimum-version handling is not enforceable. Hits F1 sections 3, 9; O1, P10. Why it breaks: F1 relies on AI Task behavior introduced around HA 2025.8, but `hacs.json` has no `homeassistant` minimum even though HACS supports that field (https://www.hacs.xyz/docs/publish/start/). Older HA installs can receive the release and fail before the "hide ai_task" branch matters. Suggested fix: set an explicit HACS minimum HA version or guarantee all AI imports and code paths are lazy and tested on the oldest supported HA.

- [MAJOR] The ai_task schema bridge is much harder than "two converters." Hits F1 section 3; O1. Why it breaks: HA structured output uses `structure` fields with `description`, `selector`, and `required`, not JSON Schema (https://www.home-assistant.io/actions/ai_task.generate_data/). JSON Schema features such as nested objects, arrays, enums, numeric constraints, nullable fields, and cross-field validation do not round-trip cleanly to selectors. Suggested fix: define a strict internal schema subset, reject unsupported constructs at startup, and snapshot both generated HA structures and JSON schemas for every task.

- [MAJOR] ai_task discovery is under-specified. Hits F1 sections 3, 5; D4, O1. Why it breaks: `has_service("ai_task","generate_data")` does not prove a usable preferred entity exists, and `entity_id=None` depends on user HA defaults; the HA docs state omitting entity uses the preferred AI task entity (https://www.home-assistant.io/integrations/ai_task/). Suggested fix: detect default availability explicitly, let the user select an AI task entity, and treat "service exists but no preferred entity" as a first-class onboarding state.

- [MAJOR] OpenAI-compatible does not mean behavior-compatible. Hits F1 section 3; P1, P10. Why it breaks: `/v1/models` plus a one-token completion does not verify JSON-schema obedience, rate-limit semantics, model-specific structured-output parameters, or provider-specific error bodies. F1 also says 429 should back off instead of skipping, which can freeze onboarding on a throttled first model while later models would work. Suggested fix: create provider adapters with capability metadata, per-model structured-output smoke tests, bounded 429 wait budgets, and recorded contract fixtures for Groq and NVIDIA.

- [MAJOR] GitHub raw remote_config is an operational single point of failure. Hits F1 section 4; D6, P1, P8, P10. Why it breaks: the design hardcodes one owner/repo/branch URL and only mentions cache/bundled fallback; it does not cover repo rename, default branch move, GitHub rate limiting, ETag handling, bad partial JSON, or a compromised maintainer account. Suggested fix: ship a signed bundled config, fetch with ETag and strict timeout, support a mirror URL, and never block startup or onboarding on the live fetch.

- [MAJOR] HACS packaging/review constraints are not reflected in the design. Hits F1 sections 2, 4, 10. Why it breaks: HACS requires runtime files for an integration to live under `custom_components/<domain>` and documents required manifest metadata and brand assets (https://www.hacs.xyz/docs/publish/integration/); F1 mentions repo scripts/datasets and new runtime pieces without saying what ships. Suggested fix: add a packaging section covering manifest requirements, HACS `homeassistant` minimum, brand assets, bundled config location, and whether ERU generation scripts are dev-only.

- [MAJOR] Iframe panel auth and mobile behavior are assumed, not designed. Hits F1 sections 2, 5, 9. Why it breaks: the current panel is an iframe registered with `async_register_built_in_panel`, and the frontend client already contains iframe-specific token recovery logic; onboarding depends on authenticated REST writes, external links, and long forms. Mobile companion apps, blocked third-party contexts, or parent-token access changes can make the gate unusable. Suggested fix: test the real HA iframe panel on desktop and companion mobile before committing to gate semantics, or move onboarding to a HA-native config flow/repair flow.

### 3. Security & privacy

- [CRITICAL] remote_config is a remote behavior-control channel without a trust boundary. Hits F1 sections 4, 7; P8. Why it breaks: `tuning` can steer battery/planner/boiler behavior from GitHub, and the design has no signature, pinned key, monotonic versioning, safety ranges, or separation between harmless defaults and runtime control. A compromised repo or bad edit can change energy behavior across installs. Suggested fix: sign remote_config, validate every value against hard-coded safe ranges, keep safety guardrails local, and require manual opt-in for any runtime-affecting tuning.

- [MAJOR] "Anonymous prompts only" is not enforceable as written. Hits F1 sections 3, 5, 10; O2, P10. Why it breaks: `validate_config` explicitly wants checks like GPS versus timezone and kWp versus capacity, while current config/options contain GPS, box IDs, API keys, entity IDs, and household energy patterns. A forbidden-token grep cannot prove raw options did not leak. Suggested fix: build prompts only from allowlisted typed DTOs, snapshot every prompt, add taint tests for box_id/GPS/API-key/entity IDs, and remove any task that requires location until the privacy model is explicit.

- [MAJOR] API key storage is treated as "not diagnostics" instead of secret handling. Hits F1 section 3; P2. Why it breaks: `.storage/oig_cloud.ai_<entry>` is plaintext in HA backups and accessible to admins/add-ons; REST masking and log masking do not address backup export, key rotation, deletion, or provider compromise. Suggested fix: add delete/rotate UI, backup/privacy disclosure, diagnostics scrub tests, no echo endpoints, and use HA's credential/secret patterns where available.

- [MAJOR] GDPR/provider disclosure is incomplete. Hits F1 sections 3, 5; P10, O2. Why it breaks: per-provider disclosure is not a privacy policy: users need to know controller/processor roles, where data goes, retention/training status, legal basis, and deletion/export implications. Household energy, tariff, and installation data can be personal data even without names. Suggested fix: add explicit consent per external provider, prefer local/ai_task paths, document data categories sent per task, and provide a no-cloud manual path.

- [MAJOR] Mandatory AI expands the blast radius of provider outage or policy changes. Hits F1 sections 3, 5; D5, P10, O2. Why it breaks: F1 makes premium access depend on Groq/NVIDIA/HA AI availability, terms, rate limits, and model deprecations, even though core sensors do not need AI. Suggested fix: decouple entitlement from provider verification; make AI a capability badge, not a dashboard unlock condition.

### 4. Migration & backward compatibility

- [CRITICAL] Removing defaults and moving solar/pricing in one release can break existing installs. Hits F1 sections 1, 7, 8; P7, D9, D11. Why it breaks: P7 says missing config becomes `unavailable`, while D11 says existing users are not gated and lose nothing. Users currently relying on implicit solar GPS/geometry, 15.36 kWh, or pricing defaults will upgrade into unavailable sensors or changed calculations with only a banner. Suggested fix: ship a preflight migration/repair release first that reports missing explicit values, then remove fallbacks only after users have confirmed or dismissed each value.

- [CRITICAL] The full-replace bug is not fixed by declaring "merge." Hits F1 section 6; P5. Why it breaks: current `OigCloudOptionsFlowHandler.async_step_wizard_summary` builds a complete payload and calls `async_update_entry(entry, options=new_options)`, while REST merge exists separately. If F1 removes fields from OptionsFlow before registry coverage is complete, unknown dashboard-only values will still be erased. Suggested fix: implement a single merge helper used by REST, options flow, migrations, and tests before deleting any steps or fields.

- [MAJOR] Grandfathering by "keys exist" preserves bad or phantom config. Hits F1 section 8; D11, P6, P7. Why it breaks: existing entries can contain dead keys, author defaults, migrated aliases, masked secret flags, or partial solar/pricing values. Marking them complete because some keys exist bypasses the new validation and can hide broken state indefinitely. Suggested fix: grandfather only dashboard access, not config validity; compute per-step `valid|needs_review|missing` from the registry and show repair items.

- [MAJOR] Silent deletion of dead keys breaks rollback. Hits F1 section 7; P6. Why it breaks: "drop at first save" means a user cannot safely downgrade to the previous HACS release if the redesign fails; older code may still expect legacy aliases or defaults even if F1 thinks they are dead. Suggested fix: keep a versioned backup of removed keys in storage for at least one release cycle and provide a restore/downgrade note.

- [MAJOR] The author's own box is a concrete migration risk. Hits F1 section 7; P7. Why it breaks: the values called out for removal are hardcoded in active code (`solar_forecast_sensor.py`, `validation.py`, planner/scenario paths). If the author's current entry never explicitly saved those same values, his box is exactly the case that will lose solar/planner behavior on upgrade. Suggested fix: run the migration preflight against a copy of that real entry and require all formerly implicit values to be explicit before release.

### 5. UX blind spots

- [CRITICAL] The paid-attention path dead-ends at the AI step. Hits F1 section 5; D5, D10, P10. Why it breaks: a user who enables the premium dashboard to configure solar/pricing can be forced into external account creation, provider outage retry, or unsupported HA AI before seeing any value. That is a lockout, not onboarding. Suggested fix: start with deterministic solar/pricing manual setup, then offer AI acceleration once available.

- [MAJOR] Offline and restricted-network installs are second-class but not declared unsupported. Hits F1 sections 4, 5, 9. Why it breaks: F1 depends on GitHub raw, Groq/NVIDIA, forecast.solar/Solcast, ERU/PDF fetches, and external account pages; the only offline story is bundled remote_config, not manual completion. Suggested fix: add an offline mode with bundled pricing, manual tariff entry, manual solar test deferral, and explicit "AI unavailable" UI.

- [MAJOR] Non-Czech users are trapped in Czech-specific assumptions. Hits F1 sections 3, 5; D1, P4, O3. Why it breaks: pricing dataset, distributors, tariff names, disclosures, and validation tasks are Czech-specific, while HACS installs are not technically prevented outside CZ unless metadata and UI enforce it. Suggested fix: hard-gate the pricing wizard by country/market, provide generic manual pricing for non-CZ users, and localize the onboarding text.

- [MAJOR] Mobile wizard ergonomics are not designed. Hits F1 section 5. Why it breaks: the onboarding flow includes account-registration instructions, external links, map/GPS, solar string geometry, graphs, pricing tables, and diff confirmation inside an iframe panel. That is likely to fail on small screens and companion apps. Suggested fix: require mobile Playwright/real-device acceptance criteria and make every external-link step resumable.

### 6. Operational

- [CRITICAL] No owner or failure policy exists for yearly pricelist updates. Hits F1 section 4; P4, O3. Why it breaks: distribution prices affect user-facing cost calculations and planner behavior, but F1 only says the dataset is generated yearly from ERU XLSX; it does not say who runs it, when, how stale data is detected, or what happens on January 1 if nobody updates it. Suggested fix: assign an owner, add an expiry date to every pricelist dataset, warn/disable autofill after expiry, and automate a release checklist.

- [MAJOR] Model-registry maintenance is a permanent support burden. Hits F1 sections 3, 4, 9; P1, P10. Why it breaks: the fallback chain is based on a point-in-time test, but the decisions already document model 404/410/503 churn. Without scheduled probes, signed registry updates, and rollback, every provider deprecation becomes onboarding support. Suggested fix: run scheduled contract probes, publish signed registry versions, and show users the exact failed provider/model state.

- [MAJOR] Retry queue semantics are missing. Hits F1 sections 3, 5, 9; P1. Why it breaks: F1 says a key can be saved unverified with a retry queue, but does not define storage, cadence, backoff, cancellation, UI notification, or whether retries run at HA startup. This can spam providers or leave users waiting forever. Suggested fix: define a persistent retry state machine with capped attempts, manual retry, repair notification, and no background retry without consent.

- [MAJOR] Support diagnostics conflict with privacy promises. Hits F1 sections 3, 9; O2, P10. Why it breaks: support will need provider/model errors, prompt task names, remote_config versions, pricing source, and onboarding state, but those can reveal household setup and provider choices. Suggested fix: define a redacted support bundle schema now and test that it excludes prompts, API keys, GPS, box IDs, and raw tariff documents.

### 7. Testability

- [MAJOR] The proposed tests do not cover upgrade/downgrade blast radius. Hits F1 section 10; P5, P6, P7, D11. Why it breaks: unit tests for dead-key filtering and grandfathering do not prove real entries from older releases survive, nor that a downgrade after F1 preserves enough data. Suggested fix: add fixture-based upgrade tests for old options/data/storage, partial configs, author-default-only configs, and downgrade backup restoration.

- [MAJOR] No adversarial remote_config tests are listed. Hits F1 sections 4, 10; P8. Why it breaks: cache/fallback/schema tests do not test malicious-but-valid values such as unsafe thresholds, huge numbers, stale pricelist years, disabled all models, or model IDs with weird strings. Suggested fix: add signed-config verification, strict bounds tests, stale-year tests, and fuzz tests for every remote field.

- [MAJOR] Prompt anonymity tests are too weak. Hits F1 sections 3, 10; O2, P10. Why it breaks: "no forbidden token in prompt" misses derived identifiers, coordinates rounded differently, entity IDs, tariff PDFs, and raw option dumps. Suggested fix: require prompt snapshot tests built from synthetic private fixtures and fail if any non-allowlisted field crosses the prompt-builder boundary.

- [MAJOR] FE tests do not exercise the real HA panel context. Hits F1 sections 5, 10. Why it breaks: Vitest and a Playwright smoke onboarding flow will not catch HA iframe token access, companion app behavior, admin/non-admin REST writes, reload races, or mobile external-link resume. Suggested fix: add HA-hosted iframe E2E tests for desktop/mobile, admin/non-admin users, reload during save, and offline/network-failure modes.

- [MINOR] The grep gate for author defaults is too narrow. Hits F1 section 10; P7. Why it breaks: `50.1219800|13.9373742|15\.36|azimuth.*138` misses equivalent values as `50.12198`, constants in generated JSON, translated defaults, or tests accidentally becoming production fixtures. Suggested fix: add semantic registry/default tests that assert required fields have no production fallback unless explicitly classified as safe.

## Ranked top-5 fix these first

1. Replace the mandatory AI unlock gate with deterministic/manual completion and AI-only capability gating.
2. Put remote_config behind signatures, strict safety bounds, expiry, and a rule that runtime guardrails stay local.
3. Add a staged migration/preflight plan before deleting defaults or moving config surfaces.
4. Fix installability: manifest runtime dependencies, HACS minimum HA version, and clean-install verification.
5. Implement one shared merge/migration path before removing old OptionsFlow fields or registry duplicates.
